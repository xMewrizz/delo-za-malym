# Работа над фронтендом

Перед изменением прочитай `README.md` в этой папке и `../docs/technical/FRONTEND.md`.
Продуктовые правила: `../docs/technical/CLIENT_FORM.md`, `CLIENT_JOURNEY.md`;
интеграция: `BACKEND.md`, `CHAT.md`. Указания пользователя имеют приоритет.

## Границы кода

- `src/app` собирает приложение: провайдеры, маршруты, общая оболочка.
- `src/pages` собирает страницы из функций и общих компонентов.
- `src/features/<name>` содержит одну функцию: API, схемы данных, query/hooks и UI.
  Экспорт наружу через `index.ts`; не импортируй внутренние файлы другой функции.
- `src/shared` содержит компоненты и утилиты без знания о кредитных продуктах.
  Он не импортирует `features`, `pages` или `app`.
- Не добавляй пустые слои или универсальные абстракции для ещё не существующих задач.
  Новые слои вводи при реальном повторении.

## Оформление

- Текущее направление по запросу пользователя — светлая банковская стилистика с
  белой округлой оболочкой на серо-лавандовом фоне, фиолетовым акцентом,
  крупной типографикой Manrope, мягкими свечениями и объёмной графикой.
  Сохраняй название проекта и рабочие сценарии.
  Значения заданы токенами; для новых функций сохраняй этот язык.

- Цвета, базовое скругление, шрифт и размеры общей оболочки находятся в
  `src/styles/tokens.css`; подключение Tailwind и глобальные правила — в `globals.css`.
- Используй семантические классы: `bg-background`, `bg-card`, `text-foreground`,
  `text-muted-foreground`, `border-border`, `text-primary`.
- Базовые элементы бери из `src/shared/ui` (shadcn/ui). Изменяй общий вариант
  компонента один раз; избегай повторяющихся переопределений на страницах.
- Отступы и сетку можно задавать шкалой Tailwind. Повторяющиеся размеры выноси в
  токены или компоненты. Не подменяй всю тему локальными hex-цветами.
- Предусматривай мобильную ширину, клавиатуру, подписи полей и состояния загрузки,
  ошибки, отсутствия данных. Учитывай `prefers-reduced-motion`.

## Данные и действия

- HTTP выполняется через `shared/api/client.ts`, схемы ответов находятся в feature API.
  Запросы вызывай через TanStack Query; ключи определяй в `model/queries.ts`.
- Серверные данные храни в query cache; локальное состояние формы — в React.
  Не копируй серверные статусы в отдельный глобальный store без причины.
- Суммы передавай строками. Не переноси скоринг, проценты или правила решения в браузер.
- После мутации используй ответ сервера и обновляй/инвалидируй связанные query.
  Передавай актуальную версию; при 409 загружай новую и предложи повторное подтверждение.
- Отправка, выбор предложения, применение изменений ассистента и подписание требуют
  действия пользователя. Не запускай их в effect. Не повторяй мутации автоматически.
- Не выдавай фиктивные данные и неготовые действия за рабочий процесс. Демоданные,
  если они нужны, изолируй и явно обозначай.
- Ключи модели и другие секреты остаются на backend; `VITE_*` доступны пользователю.

## Добавление функции

1. Зафиксируй сценарий, состояния, нужные API и критерии готовности. Шаблон: `docs/FEATURE_TEMPLATE.md`.
2. Создай небольшой модуль по примеру `features/products`, подключи его в страницу.
3. После изменений выполни `npm run check`; добавляй целевые тесты для существенных
   преобразований данных и поведения. Изменения UI также проверь в браузере.
4. Обнови документацию и `docs/ROADMAP.md`, если изменился готовый функционал.

Пакетный менеджер — npm; сохраняй `package-lock.json`. Для нового компонента shadcn:
`npx shadcn@latest add <name>`. Проверь diff: CLI может затронуть общие стили.
Не перезапускай `init` для изменения цвета темы и не перезаписывай локальные компоненты вслепую.
