# Общие форматы данных

Версия — **0.1**. Форматы обмена данными между кабинетом, ассистентом и кредитным расчётом. Примеры: [contracts/examples.json](../../contracts/examples.json).

## 1. Общие правила

- Названия полей — на английском, тексты для клиента — на русском.
- Все суммы — строки в рублях с двумя знаками: `"150000.00"`. Валюта — `RUB`. Ставка `"24.00"` означает 24% годовых.
- Даты — `YYYY-MM-DD`, месяцы — `YYYY-MM`, время — ISO 8601 с часовым поясом.
- `null` означает «неизвестно», `0` — известное нулевое значение. Не подменяем одно другим.
- Идентификаторы — строки. `application_version` связывает данные заявки, расчёт и предложения.
- Общие форматы меняем в этом документе и примерах одновременно. Переименование, удаление или изменение смысла поля требует обновления использующих его частей.

## 2. Заявка — `application`

Содержит сведения для оценки. Статус процесса хранится отдельно, история чата не заменяет поля заявки.

| Поле | Содержание |
|---|---|
| `schema_version` | Версия общего формата: `"0.1"` |
| `application_id`, `application_version` | Идентификатор и целочисленная версия заявки |
| `currency` | `"RUB"` |
| `need` | Цель, желаемый продукт, сумма, срок, дата потребности, регулярность и приоритет |
| `business` | ИНН, форма бизнеса, дата регистрации, деятельность |
| `financials` | Помесячные показатели, остаток денег, действующие кредиты и доля крупнейшего покупателя |
| `confirmation` | Версия и время последнего подтверждения клиентом; до подтверждения — `null` |
| `product_details` | Специальные данные: `overdraft` с планом операций либо `refinancing.loan_ids` с выбранными банковскими кредитами |

В `need`: `purpose`, `preferred_product`, `requested_amount`, `term_months`, `needed_by`, `recurring`, `own_funds`, `priority`. Неизвестные значения — `null`, включая неизвестную регулярность. `preferred_product: null` означает, что продукт ещё не выбран.

Необязательное `need.financing_pattern` уточняет задачу: `cash_gap` — перекрыть расходы до конкретных поступлений; `gradual_repayment` — возвращать финансирование постепенно из выручки; `null` — ещё не выяснено. Поле используется [подбором двух продуктов](PRODUCT_SELECTION.md); существующий явный выбор продукта работает и без него.

Необязательное поле `minimum_acceptable_amount` — подтверждённая клиентом минимальная сумма кредита, при которой задача остаётся выполнимой с учётом уже запланированных собственных средств. Формат — положительная денежная строка, не превышающая `requested_amount`. Отсутствие или `null` означает, что меньшую сумму нельзя включать в предложения без уточнения. Это дополнительное поле версии `0.1`; существующие заявки без него сохраняют смысл.

Цели `purpose`: `working_capital`, `investment`, `refinancing`, `contract_execution`, `other`. Приоритет `priority`: `lowest_payment`, `lowest_total_cost`, `preserve_amount` либо `null`.

Продукты: `working_capital_loan`, `overdraft`, `revolving_credit_line`, `investment_loan`, `refinancing`.

В `business`: `inn`, `legal_form` (`ip` или `ooo`), `registered_at`, `activity`. ИНН — строка, не число.

В `financials`:

- `monthly`: записи с `month`, `operating_inflow`, `operating_outflow`, `taxes`. Расходы не включают налоги и обслуживание кредитов; кредитные поступления и переводы между своими счетами не входят в операционные поступления. Здесь только фактические показатели.
- `cash_balance`: текущие собственные деньги.
- `existing_loans`: действующие кредиты с `loan_id`, `outstanding_principal`, `monthly_payment`, `maturity_date`. У оформленных в кабинете кредитов также есть `application_id`, `product_id` и `schedule`. В `monthly_payment` передаётся максимальный платёж полного графика, включая период после отсрочки основного долга. `[]` означает подтверждённое отсутствие кредитов, `null` — что сведения ещё неизвестны.
- Открытая возобновляемая линия дополнительно имеет `is_commitment: true`, `product_id: "revolving_credit_line"`, `credit_limit` и `accrued_interest`. В `outstanding_principal` — фактический долг, в `monthly_payment` — резерв нагрузки по всему лимиту. Это защищённые банковские данные; реальные платежи видны в API линии и календаре.
- `largest_buyer_share`: доля от 0 до 1 за представленные месяцы, например `0.25`; при отсутствии сведений — `null`.

Дополнительный объект `product_details.overdraft` определён в [описании овердрафта](OVERDRAFT.md#2-входные-данные). Для [рефинансирования](REFINANCING.md) передаётся `product_details.refinancing: {"loan_ids": ["existing-001"]}`; остатки и графики берутся из банковского профиля, сумма выводится сервером. [Линия](REVOLVING_CREDIT_LINE.md) использует сумму запроса как лимит. [Инвестиционный кредит](INVESTMENT_LOAN.md) добавляет в `need` стоимость проекта, собственный взнос и отсрочку.

## 3. Предложение — `offer`

| Поле | Содержание |
|---|---|
| `offer_id` | Идентификатор предложения |
| `application_id`, `application_version` | К каким данным относится |
| `product_id` | Код продукта |
| `amount`, `term_months` | Сумма и срок |
| `annual_rate_percent` | Номинальная ставка в процентах годовых |
| `monthly_payment` | Регулярный ежемесячный платёж; у инвестиционного кредита — максимум после отсрочки; для лимитов может быть `null` |
| `fees_total`, `total_repayment` | Комиссии за весь расчёт и общая сумма выплат с комиссиями |
| `conditions` | Условия до подписания: объекты с `code`, `message`, `fulfilled`; `[]`, если дополнительных условий нет |
| `valid_until` | Срок актуальности предложения |

Для разового кредита и рефинансирования `total_repayment` включает основной долг, проценты и комиссии. Датированный график возвращается в `schedule` предложения и результата завершения. Рефинансирование дополнительно возвращает `refinancing` со сравнением текущих и новых выплат. Для овердрафта стоимость зависит от сценария использования.

У предложения `overdraft`: `amount` — лимит; `term_months`, `monthly_payment`, `total_repayment` — `null`. Добавлены `agreement_months` (срок договора), `max_debt_days` (срок возврата выборки) и `scenario_cost` с `start_date`, `end_date`, `required_limit`, `total_drawn`, `total_interest`, `total_repayment`. Суммы в `scenario_cost` относятся только к указанному плану, а не ко всем будущим операциям по договору. Расчёт и формат плана: [овердрафт](OVERDRAFT.md).

В примерах аннуитетный платёж и проценты за каждый месяц округлены до копеек по правилу HALF_UP. Последний платёж закрывает остаток: он может отличаться на несколько копеек, поэтому общие выплаты не всегда равны `monthly_payment × term_months`.

## 4. Результат оценки — `assessment`

| Поле | Содержание |
|---|---|
| `schema_version` | `"0.1"` |
| `assessment_id` | Идентификатор оценки |
| `application_id`, `application_version` | Оценённая версия |
| `stage` | `preliminary` — подбор до отправки; `final` — банковское рассмотрение |
| `outcome` | Один из результатов ниже |
| `risk_grade` | `low`, `medium`, `high` или `null`, если риск ещё не оценён |
| `reasons` | Причины: объекты с `code` и понятным `message` |
| `required_information` | Уточнения: `field`, `code`, `question`; без уточнений — `[]` |
| `offers` | Полные объекты предложений; при отсутствии — `[]` |
| `policy_version`, `catalog_version` | Версии правил и условий продуктов |
| `calculated_at` | Время расчёта |

Значения `outcome`:

- `approved` — исходный запрос проходит.
- `alternative_offers` — предложены другие параметры или продукт.
- `conditional_approval` — исходный запрос проходит при дополнительных условиях.
- `needs_information` — нужны сведения для решения.
- `declined` — отказ.
- `out_of_policy` — ситуация не покрывается правилами автоматической оценки.

При `needs_information` список уточнений непустой, предложения в первой версии не выдаём. При отказе и `out_of_policy` предложений также нет. При остальных исходах есть хотя бы одно предложение. Если альтернативный вариант требует дополнительных условий, это видно в его `conditions`, а результат остаётся `alternative_offers`.

Предварительная оценка имеет ту же структуру, но её предложения нельзя принять для подписания. Ошибка сервиса не становится результатом `declined`.

## 5. Состояние заявки — `application_state`

Поля: `application_id`, `application_version`, `status`, `current_step`, `latest_assessment_id`, `selected_offer_id`, `next_action`, `updated_at`. Неизвестные ссылки — `null`.

Статусы: `draft`, `submitted`, `under_review`, `waiting_for_data`, `check_retry_pending`, `offers_ready`, `conditions_pending`, `ready_to_sign`, `signed`, `disbursed`, `limit_opened`, `declined`, `out_of_policy`, `offer_expired`, `cancelled`.

`current_step`: `data_collection`, `product_selection`, `data_validation`, `external_checks`, `risk_assessment`, `offer_calculation`, `offer_selection`, `conditions_check`, `signing`, `completion`.

`next_action` — подсказка интерфейсу: `type` и `label`. Типы: `complete_profile`, `confirm_submission`, `provide_information`, `wait`, `select_offer`, `fulfill_conditions`, `sign`, `request_reassessment`, `none`. Подсказка не заменяет проверку допустимости действия сервером.

Основной путь: `draft → submitted → under_review → offers_ready → ready_to_sign → signed → disbursed / limit_opened`. Уточнения возвращают к рассмотрению после подтверждения новых данных. Перед подписанием выполняются дополнительные условия, если они есть.

Отправленные версии неизменяемы. Подтверждённое дополнение после отправки создаёт новую версию и делает прежние предложения неактуальными. Подписать можно только выбранное актуальное предложение этапа `final`, после выполнения всех условий.

Перед переходом к подписанию backend вызывает общую [проверку выбранного предложения](OFFER_READINESS.md): актуальность версии, итоговой оценки, срока предложения и выполнения условий.

`outcome` описывает результат расчёта, `status` — положение заявки в процессе. Например, оценка вернула альтернативы, а заявка находится в `offers_ready`.

## 6. Что передаёт ассистент

Ассистент предлагает изменения полей, а не возвращает заново всю заявку. Минимальный формат: `intent`, `application_id`, `base_application_version`, `changes` (поле → значение), `question` (строка или `null`).

Намерения `intent`: `propose_changes`, `simulate_alternative`, `ask_clarification`, `answer_question`. Рабочий диалоговый API также поддерживает `compare_options` с отдельными предпочтениями для подбора; его формат описан в [документации чата](CHAT.md). Пример изменения поля: `"need.requested_amount": "800000.00"`.

Backend проверяет разрешённые поля и актуальность базовой версии; клиент подтверждает применение изменений. Для `simulate_alternative` нужен отдельный расчёт; в тестовом чате это намерение пока не используется. Ассистент не меняет статус, решение, подтверждение или условия продукта. В текущем [диалоговом API](CHAT.md) допускаются изменения отдельных полей `need`; сведения о существующем бизнесе предзаполнены, полученные из банка финансовые показатели доступны для просмотра; дополнить можно только отсутствующие значения.

## 7. Ответственность модулей и примеры

**Андрей** строит формы и карточки по этим полям, сохраняет подтверждения и управляет состояниями. **Тимофей** принимает заявку и результаты проверок, возвращает `assessment` с предложениями или уточнениями. **Илья** возвращает предлагаемые изменения и объясняет полученный `assessment`.

В [примерах](../../contracts/examples.json) есть полная заявка первого продукта, внешние проверки, ответ ассистента, шесть исходов оценки и состояние заявки. HTTP-операции подтверждения, выбора предложения, подписания и завершения описаны в [backend](BACKEND.md). Формат загрузки документов пока не определён.

`demo-001` связывает заявку, альтернативное предложение и состояние. Остальные оценки — независимые примеры для отображения разных результатов. ИНН `0000000000` — идентификатор тестового клиента в симуляторе; правила реального формата ИНН проверяются отдельно.

## 8. Внешние проверки

Объект `checks` передаётся в модуль рассмотрения отдельно от заявки. Это результаты доверенного симулятора/backend, а не поля, которые может установить LLM или клиент. Ответы привязаны к конкретной версии подтверждённых данных.

| Поле | Содержание |
|---|---|
| `schema_version` | `"0.1"` |
| `application_id`, `application_version` | Идентификатор и версия проверенной заявки |
| `business_inn` | ИНН проверенного бизнеса |
| `checked_at` | Время проверки с часовым поясом, не позднее времени оценки |
| `registration` | `status`, `active`; для действующего бизнеса также `registered_at`, `legal_form` |
| `restrictions` | `status`, `financing_prohibited` — общий запрет по правилам симулятора |
| `credit_history` | `status`, `category` |
| `obligations` | `status`, `matches_application` — совпадают ли обязательства с данными заявки |

Статусы секций: `completed`, `pending`, `error`. Полезная нагрузка секции учитывается только при `completed`. `active`, `financing_prohibited`, `matches_application` — строго логические значения. Категории истории: `good`, `no_history`, `minor_delinquency`, `serious_delinquency`; их баллы определены в [скоринге](SCORING.md).

Демонстрационный срок актуальности проверок — 24 часа. Неактуальные или незавершённые ответы требуют получения новых результатов. Техническая ошибка означает ожидание повтора проверки. Эти состояния передаются через внешний результат `AssessmentResult`, без фиктивного кредитного `assessment`; см. [интерфейс рассмотрения](ASSESSMENT.md#2-результат-и-процесс).

## Инвестиционный проект

`need.preferred_product: "investment_loan"`, `purpose: "investment"`; `project_cost` и `own_funds` — суммы строками, `principal_grace_months` — 0/3/6, `term_months` — общий срок. `requested_amount` вычисляется сервером как разница стоимости и взноса. Предложения включают параметры проекта, проценты во время отсрочки и полный график. [Правила и примеры](INVESTMENT_LOAN.md).
