# Контракт вопроса и автоматический повтор модели

22 октября 2026. Изменения проверены `senior-prompt-engineer` и `agent-regression-evals`; исходная серия — [41/45 испытаний](agent-regression-evals-2026-10-22.md).

## Что изменилось

В `backend/assistant.py` устранено противоречие в инструкции извлечения: известные параметры заполняет модель, недостающие сведения уточняет приложение. `FactsExtractionReply.question` теперь принимает только null; произвольные объекты и строки не заменяют карточки приложения. Для общего `AssistantReply.question` по-прежнему допустимы строка/null. Инструкция также требует строковый `text` и объяснение ограничения для недопустимой команды без изменения потребности и плана.

Статическая оценка промпта: clarity 67 → 67, приблизительный размер 1027 → 1060 токенов (+3,2%). Структурный gate скилла пройден. Эти эвристики не измеряют качество ответов; проверка поведения выполнена отдельной полной серией ниже. Шаблоны «экспертной роли» и дополнительные примеры не добавлялись.

В `scr/delo_za_malyn/Models/Llm/client.py` добавлен автоматический повтор **одного запроса генерации, максимум один раз**:

| Событие | Действие |
|---|---|
| Timeout, обрыв соединения | Один повтор того же payload |
| HTTP 408/500/502/503/504 | Один повтор; учитывается короткий `Retry-After` |
| HTTP 200, но нет текста и tool calls | Один повтор; reasoning не считается пользовательским ответом |
| Корректный ответ только с tool calls | Успех, повтор не нужен |
| HTTP 400/401/402/403/404/422/429 | Ошибка без автоповтора |
| Неверный JSON/протокол, запрещённые изменения, обрезанный ответ, переполненный контекст | Строгая ошибка без автоповтора |
| Вторая попытка тоже не удалась | Ошибка возвращается пользователю, цикл прекращается |

По умолчанию пауза 0,5 секунды. Для HTTP допустим `Retry-After` до двух секунд; более длинный срок запрещает немедленный повтор. У хода кабинета остаётся прежний `HTTP_TIMEOUT_SECONDS`: первая попытка генерации получает половину оставшегося бюджета, вторая — остаток после паузы. При полном бюджете 120 секунд первая попытка ждёт около 60 секунд. Сетевой timeout задаётся urllib; фактическое измеренное завершение ожидания может быть немного позже, что видно в трассах.

Повтор расположен перед передачей ответа агента на исполнение: уже выполненные инструменты, запись сообщений, сохранение сравнения и подтверждение заявки не запускаются заново. Для этапа финального объяснения повторяется только объяснение по готовым результатам. Несколько генераций внутри одного хода могут иметь по одному повтору и делят общий бюджет хода. На стороне провайдера оборванный запрос мог уже вызвать генерацию, поэтому дополнительный запрос может расходовать его ресурсы.

Сценарий исправления плана стал нестабильным в данной серии; приписывать это изменение логике модели по одному транспортному сбою нельзя.

Для всех 45 испытаний зафиксированы сохранённые данные заявки и состояние draft. Проверка трасс дала `ALL_MATCH`, 45/45, запрещённых tool calls нет. Для обоих критических сценариев результат 3/3; неудачный сценарий не исключён.

## Как читать сравнение

- `flake_detector.py`: **FLAKY_CASES**, exit 2 — один нестабильный сценарий, `pending_plan_correction`; 14 стабильных успехов, стабильных провалов нет.
- `trajectory_checker.py`: **ALL_MATCH**, exit 0.
- `regression_gate.py`: **PASS**, exit 0 по его статистическим критериям. Среднее изменение доли успехов по сценариям +0,0667, 95% CI **[−0,0924; +0,2258]**, McNemar p=1,0. Ни один baseline-сценарий не потерян, карантин пуст.

Набор из 15 сценариев мал, а доверительный интервал широк: статистически доказанного повышения надёжности здесь нет. Более того, один ранее стабильный сценарий теперь имеет провал. Автоматический PASS сравнительного скрипта не заменяет это наблюдение; утверждение «регрессий нет» не делается. Повтор устраняет часть временных сбоев, но не гарантирует ответ при длительной недоступности провайдера.

## Проверки реализации

Python: **383 обнаруженных теста, 382 успешных и один пропущен**. Отдельные UI/API-интеграции с настоящим временным FastAPI: **9/9**.

Добавлены девять тестов повторов и проверка строгого владения вопросами в извлечении фактов. Проверены:

- повтор того же payload при временных сетевых/HTTP-ошибках и пустом ответе;
- прекращение после второй неудачи, отказ от повтора при ошибке ключа, квоты, протокола и контекста;
- соблюдение длинного `Retry-After` и общего бюджета вложенных запросов;
- отсутствие ключа, тела ошибки и приватных деталей в диагностике;
- ровно одно исполнение инструмента, один сохранённый расчёт и одна пара сообщений после сбоя финального объяснения;
- повтор того же `request_id` не создаёт дубль, а после двух неудачных попыток нет частично сохранённого сообщения;
- объект/строка `question` в извлечении не исправляются незаметно и не меняют заявку;
- классификатор eval различает первоначальный timeout и финальный обрыв соединения.
