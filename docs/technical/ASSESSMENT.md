# Рассмотрение первого продукта

Модуль: [credit_engine/assessment.py](../../credit_engine/assessment.py). Каталог: разовый кредит на оборотные цели. Правила: `demo-v1`. Другие продукты этой версией не оцениваются.

Готовые входы и полные рассчитанные ответы: [семь сценариев для интеграции](SCENARIOS.md).

## 1. Вызов

```python
import json
from pathlib import Path
from credit_engine import assess_application

examples = json.loads(Path("contracts/examples.json").read_text(encoding="utf-8"))
result = assess_application(
    examples["application"],
    examples["checks"],
    calculated_at="2026-10-20T12:01:00+03:00",
    assessment_id="assessment-demo",
)
payload = result.to_dict()
```

Время оценки передаётся явно с часовым поясом. `assessment_id` необязателен; по умолчанию создаётся UUID. `stage` — `final` по умолчанию или `preliminary`. Для `final` требуется подтверждение текущей версии заявки не позднее времени оценки. Оба этапа требуют завершённых внешних проверок для расчёта класса риска; предварительное предложение не разрешает подписание.

## 2. Результат и процесс

| `result.status` | Содержание |
|---|---|
| `assessed` | В `assessment` результат по общему контракту `0.1` |
| `invalid_data` | Ошибки формата; `assessment = null` |
| `needs_checks` | Проверки отсутствуют, не завершены, устарели или относятся к другой версии/бизнесу; `assessment = null` |
| `check_retry_pending` | Техническая ошибка проверки; `assessment = null` |

`issues` содержит ошибки с `field`, `code`, `message`. `financial_metrics` и `scoring` содержат рассчитанные внутренние показатели, если соответствующий этап выполнен. `to_dict()` формирует JSON-совместимый результат, сохраняя `Decimal` строками.

В `assessment` входят идентификаторы и версия заявки, этап, исход, класс риска, причины, уточнения, предложения, версии правил и время расчёта. Backend использует `result.status` для управления проверками, а `assessment.outcome` — для показа кредитного результата. Ошибка проверки не превращается в отказ или вопрос клиенту.

## 3. Последовательность оценки

1. Проверка формата, обязательных полей и подтверждения версии.
2. Проверка области применения: рубли, ИП/ООО, оборотная цель и первый продукт.
3. Расчёт финансовых показателей и проверка внешних результатов.
4. Общие ограничения: прекращение деятельности или установленный запрет означают отказ. Расхождения регистрации или обязательств требуют уточнений.
5. Возраст бизнеса и применимость модели денежных потоков. Менее 12 полных месяцев или положительное среднее с неположительным отдельным месяцем означают `out_of_policy`.
6. Расчёт риска по [балльным правилам](SCORING.md). Высокий риск исключает этот продукт; средний требует поручительства.
7. Проверка суммы, срока и максимального фактического платежа по всему графику. Сравнение с округлённым регулярным платежом недостаточно.
8. Расчёт альтернатив, если исходный запрос не проходит.

Нулевая доступная нагрузка и отсутствие допустимых условий дают отказ в рамках текущего каталога. Это не утверждение о доступности всех продуктов банка. Поручительство не повышает доступную нагрузку.

## 4. Альтернативы

Сначала проверяются допустимые сроки для всей запрошенной суммы. Меньшая сумма рассчитывается по шагу 10 000 ₽ с повторной проверкой полного графика. Максимум ищется по дискретным суммам; кандидат не превышает запрос и лимит продукта.

Для меньшей суммы требуется `need.minimum_acceptable_amount`: минимальная сумма кредита, при которой клиент подтвердил выполнимость задачи с учётом уже запланированных собственных средств. `null` означает отсутствие подтверждения. Поле не позволяет повторно учитывать `own_funds` как дополнительное покрытие разницы.

При подтверждённом минимуме выбирается меньшая сумма на исходном допустимом сроке; если её недостаточно и нет варианта на всю сумму, проверяются остальные сроки. Если минимальная сумма не известна, но есть вариант на всю сумму, показывается этот вариант. Если доступны только меньшие суммы, результат — `needs_information` с вопросом о минимуме, без предложения к выбору.

Сравнение кандидатов:

| Приоритет | Порядок |
|---|---|
| `preserve_amount` или `null` | Больше сумма, затем меньше проценты, затем короче срок |
| `lowest_payment` | Меньше максимальный платёж, затем больше сумма, затем меньше проценты |
| `lowest_total_cost` | Меньше суммарные проценты, затем больше сумма, затем короче срок |

В первой версии комиссии нулевые, поэтому стоимость финансирования для ранжирования равна процентам. Приоритет применяется к альтернативам: если исходный запрос проходит, он сохраняется. Возвращается не более двух предложений. Изменённые сумма или срок дают `alternative_offers`; требование поручительства сохраняется в `conditions`.

## 5. Внешние проверки и настройки

Формат `checks` приведён в [общем контракте](CONTRACTS.md#8-внешние-проверки). Проверки привязаны к заявке, её версии и ИНН; срок актуальности — 24 часа. Будущая дата и время без часового пояса не принимаются. Дата регистрации и правовая форма сверяются с результатом проверки; обязательства — по `matches_application`.

`WorkingCapitalPolicy` содержит суммы, шаг, сроки, ставку, минимальный возраст и сроки актуальности. `FinancialPolicy` задаёт период истории и долю обслуживания долга. Версии этих политик должны совпадать; при изменении правил используется новая версия. Версия скоринга отдельно присутствует во внутреннем результате `scoring`.

Модуль принимает готовые результаты симулятора. Он не обращается к внешним банковским сервисам, не сохраняет заявку и не выполняет подписание.
