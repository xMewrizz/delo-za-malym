# Сценарии для подключения расчёта к кабинету и ассистенту

В [contracts/scenarios](../../contracts/scenarios) находятся семь полных примеров «вход → результат `assess_application`». Каждый файл можно использовать отдельно. База и сервер модели для запуска не нужны.

| Файл | Что показывает |
|---|---|
| `01_approved.json` | 500 тыс. ₽ на год: исходный запрос одобрен |
| `02_longer_term.json` | Миллион на год не проходит; предложен миллион на 18 месяцев |
| `03_lower_amount.json` | Подтверждён минимум 700 тыс. ₽ и приоритет меньшей стоимости: первым предложены 740 тыс. ₽ на год; вторым — миллион на 18 месяцев |
| `04_needs_information.json` | Нет доли крупнейшего покупателя: запрашивается `financials.largest_buyer_share` |
| `05_guarantor_required.json` | 500 тыс. ₽ на год: требуется поручительство |
| `06_declined.json` | Общий запрет на финансирование: отказ без предложений |
| `07_check_unavailable.json` | Ошибка сервиса кредитной истории: ожидание повтора без кредитного решения |

## Запуск

Из корня репозитория проверить все сохранённые ответы:

```shell
python -m scripts.run_credit_scenarios
```

Посмотреть список сценариев:

```shell
python -m scripts.run_credit_scenarios --list
```

Получить настоящий рассчитанный ответ одного сценария в JSON:

```shell
python -m scripts.run_credit_scenarios --scenario 03_lower_amount --json
```

Команда каждый раз вызывает кредитный модуль и сравнивает полный ответ с сохранённым. Совпадение даёт `OK` и код завершения 0; расхождение — `FAIL`, разницу в stderr и код 1. В режиме `--json` stdout содержит только рассчитанный ответ. Примеры не перезаписываются.

## Что внутри файла

- `scenario_id`, `title`, `description` — название и смысл примера.
- `input.application` — полная заявка, включая подтверждённую версию.
- `input.checks` — готовый ответ симулятора внешних проверок для той же заявки.
- `input.calculated_at`, `stage`, `assessment_id` — параметры вызова.
- `expected` — полный сохранённый ответ `result.to_dict()`: `status`, `assessment`, `issues`, `financial_metrics`, `scoring`.

Время и идентификатор оценки зафиксированы, поэтому результат воспроизводится, включая сроки актуальности и идентификаторы предложений. Для просмотра используйте указанное в примере время. В работающем приложении backend задаёт текущее время и получает актуальные проверки; простая замена времени на сегодняшнее не обновляет сведения клиента.

## Как обрабатывать ответ

Сначала проверяем **`result.status`**, затем — **`result.assessment.outcome`**, только если `status == assessed`.

| `result.status` | Действие приложения |
|---|---|
| `assessed` | Сохранить оценку и обработать её `outcome` |
| `invalid_data` | Показать ошибки из `issues` у соответствующих полей; кредитного решения нет |
| `needs_checks` | Получить или обновить внешние проверки и повторить оценку |
| `check_retry_pending` | Показать ожидание проверки и организовать повтор; отказа нет |

При `assessed`:

| `assessment.outcome` | Что показываем и какое состояние используем |
|---|---|
| `approved`, `alternative_offers`, `conditional_approval` | Карточки из `offers`, объяснение `reasons`; для окончательного рассмотрения — `offers_ready` |
| `needs_information` | Поля и вопросы из `required_information`; `waiting_for_data` |
| `declined` | Причины отказа; `declined` |
| `out_of_policy` | Причину ограничения автоматической оценки; `out_of_policy` |

Поручительство отображаем из `offer.conditions`. В `conditions_pending` переходим после выбора клиентом такого предложения. Предварительный подбор (`stage = preliminary`) не переводит отправленную заявку в готовность к подписанию.

**Андрей:** может сначала подставлять `expected` для отображения состояний, затем заменить заглушку настоящим вызовом. Числа и условия карточек берутся из `assessment.offers`. Состояние заявки изменяет backend, сам расчёт его не сохраняет.

**Илья:** объясняет клиенту `reasons`, `offers`, `required_information`. При техническом сбое использует `status` и `issues`, поскольку `assessment` отсутствует. `financial_metrics` и `scoring` нужны для расчётного контекста; их внутренние статусы не заменяют итог рассмотрения.

После ответа на уточнение сохраняется новая подтверждённая версия и выполняются привязанные к ней проверки. После восстановления сервиса повторяется оценка текущей версии. Оба продолжения проверяются в [tests/test_scenarios.py](../../tests/test_scenarios.py).
