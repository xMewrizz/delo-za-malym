# Тестовая страница диалога

Страница **`/chat`** работает на существующем FastAPI. Переписка сохраняется в SQLite, рядом отображается потребность и настоящий результат кредитного расчёта. Можно заполнять форму вручную, подтверждать изменения от ассистента, подбирать продукт и рассчитывать выбранный вариант.

## Запуск

```shell
docker compose up --build -d
```

Открыть **http://localhost:8000/chat**. Если в `.env` выбран другой `API_PORT`, использовать его. В корневом шаблоне выбран `CHAT_MODE=demo`. Для проверки фиксированных примеров без генерации можно указать `CHAT_MODE=demo`.

Для запуска без Docker:

```shell
uv run --env-file .env --frozen uvicorn backend.main:app --host 127.0.0.1 --port 8000
```

Кабинет использует корневой `.env` (шаблон `.env.example`). Лабораторный `scr/delo_za_malyn/settings/.env` можно явно передать через `--env-file` вместо него.

не использует Dahl. [Подключение модели](../LLM_MODES.md).

## Подключение модели

В корневом `.env` указать:

```dotenv
CHAT_MODE=model
LLM_API_BASE_URL=http://127.0.0.1:11434/v1
LLM_DOCKER_API_BASE_URL=http://host.docker.internal:11434/v1
LLM_MODEL=имя-модели-на-сервере
LLM_API_KEY=
HTTP_TIMEOUT_SECONDS=60
```

Перезапустить `docker compose up -d`. Адрес должен вести на OpenAI-совместимый API модели. Python на компьютере использует `LLM_API_BASE_URL`; Compose передаёт контейнеру адрес из `LLM_DOCKER_API_BASE_URL`. Название модели берётся из `/v1/models`. Сервер модели запускается отдельно; веса в образ кабинета не включены.

Используется существующий `scr/delo_za_malyn/Models/Llm/client.py`. Ключ передаётся только сервером. Для лабораторного запуска остаётся отдельный шаблон `scr/delo_za_malyn/settings/.env.example`. В контейнер передаются только параметры сервиса; файл с ключом Tavily не копируется в образ.

таймаут — 120 секунд. После изменения настроек: `docker compose up -d`.

Контейнер содержит FastAPI и SQLite; модель остаётся в Ollama на компьютере.
Веса и локальные `.env` исключены из контекста сборки. Открытие `/chat`, `/docs`
или `/health` не запускает генерацию: первый запрос к модели происходит после

Чат использует `SYSTEM_PROMPT` из `backend/assistant.py`.

Сценарные промпты и RAG пока не подключены. Ответ приходит целиком после генерации. Отдельный лабораторный API
из [LLM_CHAT_API.md](LLM_CHAT_API.md) не следует запускать одновременно на порту 8000.

## Контракт диалогового модуля

В [backend/assistant.py](../../backend/assistant.py) находятся `SYSTEM_PROMPT`, сбор контекста и `ModelAssistant.reply(messages)`. Здесь можно улучшать диалог или подключить свой агент, сохранив вход и выход. При создании приложения также можно передать `create_app(assistant=...)` для отдельного диалогового модуля.

На вход поступают сообщения OpenAI-формата: инструкция, текущая заявка, состояние процесса, каталог, результат расчёта/подбора, статусы прошлых предложений и вся история текущего диалога. На выходе нужен объект:

```json
{
  "text": "Предлагаю изменить срок на 18 месяцев. Подтвердите изменение.",
  "intent": "propose_changes",
  "changes": {"need.term_months": 18},
  "question": null
}
```

Намерения: `propose_changes`, `ask_clarification`, `answer_question`, `compare_options`. При уточнении или ответе `changes` пустой. В `changes` доступны отдельные поля `need` из [контрактов](CONTRACTS.md). Будущие операции передаются через `overdraft_plan`; фактические финансовые показатели и данные бизнеса модель не меняет. Изменения суммы возвращаются строкой рублей с двумя знаками.

### Сбор потребности

Новые суммы, сроки, собственные средства и достаточный минимум обрабатываются коротким запросом `extract_facts` без расчётных инструментов. Модель возвращает типизированные факты и вопрос; адаптер определяет `propose_changes`, если есть изменения. Поэтому уточняющий вопрос не теряет уже названные поля. Расчёты и сравнение вызываются отдельно по просьбе клиента, подтверждение остаётся явным.

### Проверка настоящей модели

```shell
docker compose exec api python -m scripts.run_dialogue_evaluation --output /tmp/dialogue-evaluation.json
```

Команда использует 15 синтетических сценариев из `contracts/dialogue_cases.json`, временную SQLite и настроенный API модели. Проверяются суммы и сроки, исправления, относительные даты, сравнение, банковские факты и сохранение заявки до подтверждения. Запуск расходует квоту провайдера. Для повторной проверки одного случая: `--case loan_request`; отчёт можно скопировать из контейнера через `docker cp`. Локально используется `uv run --env-file .env --frozen python -m scripts.run_dialogue_evaluation`.

### Будущие операции овердрафта

Для операций общий контракт диалога содержит отдельный `overdraft_plan` при `intent=propose_changes`. Внутри `ModelAssistant.extract_facts` используется короткий контекст с датой, известными кредитами и текущим планом; провайдер возвращает `text`, `changes`, `overdraft_plan`, `question` без `intent`. Адаптер определяет намерение, приложение формирует текст карточки и вопросы по пропускам. Инструменты расчёта на этапе сбора не вызываются. Пример общего ответа:

```json
{
  "text": "Уточните дату поступления и платежи по текущим кредитам.",
  "intent": "propose_changes",
  "changes": {},
  "overdraft_plan": {
    "transactions": [
      {"transaction_id": "purchase-1", "direction": "outflow", "date": "2026-10-22", "amount": "450000.00"},
      {"transaction_id": "receipt-1", "direction": "inflow", "date": null, "amount": "500000.00"}
    ]
  }
}
```

В следующем сообщении передаются тот же `transaction_id` и только дополненные поля. Неизвестные дата и сумма остаются `null`; удаление задаётся через `removed_transaction_ids`. `loan_id` связывает расход с действующим кредитом, `cash_reserve` задаёт явно названный запас. `debt_payments_confirmed=true` передаётся после подтверждения полноты кредитных платежей за период либо их отсутствия.

Остаток приложение берёт из профиля, новый период начинается текущим днём и покрывает даты операций. В контексте есть `current_datetime` по Москве и `timezone=Europe/Moscow` для понимания «завтра» и «через неделю». Модель не задаёт банковские показатели, остаток или границы периода.

План накапливается в `proposal.changes["product_details.overdraft"]`, пропуски возвращаются в `proposal.plan_issues`. До подтверждения заявка и расчёт остаются прежними. Неполный план подтвердить нельзя (`plan_incomplete`, HTTP 422). После подтверждения план сохраняется в форму и автоматически запускается отдельный расчёт овердрафта. Выбор предложения и отправка заявки выполняются отдельно.

В карточке можно исправить или удалить операции. Запрос `/proposals/{id}/edit` принимает обычные `changes` потребности и дополнительный `overdraft_plan`; `remove_overdraft_plan=true` убирает план из предложения. Если план в форме или используемые банковские данные изменились, требуется проверить актуальную карточку и сохранить правки. Изменение другого поля потребности не мешает подтверждению.

Backend накапливает изменения в общем черновике: новый срок дополняет предложенную сумму, а обычный вопрос не отменяет карточку. В ней можно исправлять значения и убирать отдельные поля. Пока пользователь не нажал «Подтвердить», заявка не меняется. Если форма параллельно изменила другое поле, черновик можно применить к актуальной версии. При конфликте того же поля требуется проверить и сохранить правки черновика. Подтверждение и изменение заявки сохраняются одной транзакцией.

`compare_options` запускает настоящий расчёт нескольких условий разового кредита, сохраняя заявку. В ответе модели: `changes: {}`, `preferences` — необязательные настройки `requested_amount`, `maximum_monthly_payment`, `minimum_term`, `maximum_term`, `preserve_amount`, `priority`. Суммы — строки рублей. Сохранённый результат доступен в интерфейсе сразу и в контексте следующего сообщения. Модель не должна заранее утверждать результаты ещё не выполненного расчёта.
API запрашивает структурированный ответ (`LLM_RESPONSE_FORMAT=json_schema` либо `json_object`), затем проверяет JSON и допустимость изменений. В общем ответе `AssistantReply.question` допускает строку/null. В отдельном извлечении фактов `FactsExtractionReply.question` всегда null: уточняющие карточки формирует приложение. Модель не может подменить их объектом со своими полями и кнопками.

Для каждого запроса генерации автоматически допускается **один повтор** при timeout, обрыве соединения, HTTP 408/500/502/503/504 или пустом ответе. Пауза — 0,5 секунды; для HTTP учитывается `Retry-After`, если он не превышает двух секунд. При большем значении повтор в этом запросе не выполняется. HTTP 400/401/402/403/404/422/429, неверные аргументы/JSON, небезопасные изменения, лимит контекста и обрезанный ответ не запускают повтор.

Повтор отправляет тот же payload внутри LLM-клиента. Он не запускает повторно ход диалога, исполнение инструментов, сохранение сравнения или подтверждение заявки. Общий `HTTP_TIMEOUT_SECONDS` на ход кабинета не увеличивается: первой попытке генерации выделяется половина оставшегося бюджета, второй — остаток после паузы. Например, при полном бюджете 120 секунд первая попытка ждёт до 60 секунд. Несколько этапов модели делят один бюджет хода. Поскольку провайдер мог обработать запрос до обрыва соединения, повтор может означать дополнительную генерацию на его стороне.

Если разрешённый повтор также не удался, возвращается исходная категория ошибки. Неверный контракт — `assistant_invalid_response`, соединение или ожидание — `assistant_unavailable`. В лог пишутся причина, номер попытки и класс ошибки без текста диалога, тела ответа провайдера и ключей. Неполная пара сообщений и результаты неуспешного хода не сохраняются. Полные eval-прогоны записывают исход каждой попытки, поэтому восстановление после повтора не скрывает исходный сбой.

Ошибки протокола LLM выделены отдельно: HTTP 502 `assistant_empty_response`,
`assistant_unparsed_tool_call`, `assistant_invalid_response` или
`assistant_invalid_json`. Сообщение объясняет конкретный сбой; HTTP 200 от Ollama
сам по себе не гарантирует наличия пригодного ответа. Лог содержит фиксированную
категорию и флаг наличия reasoning, но не его содержимое. Обычный текст на этапе
выбора инструментов допускает последующее форматирование и больше не создаёт
ложного предупреждения `json_invalid`.

После JSON допускаются только известные служебные суффиксы Gemma; сам JSON
не исправляется, лишние поля и произвольный текст по-прежнему отвергаются.
Если `calculate_loan` уже успешно отработал, а финальное объяснение нарушило
формат или лимит вывода, сервер сохраняет точный результат инструмента и
показывает явное сообщение об отсутствии объяснения. Изменений заявки при этом
нет; после исчерпания разрешённых попыток точный результат калькулятора остаётся доступен. Без успешного калькулятора такой подстановки нет.

Для малого окна `LLM_CONTEXT_SIZE` перед запросом оценивается размер сообщений,
описаний инструментов и схемы ответа по UTF-8, с резервом до 1024 токенов генерации.
Это приближённая проверка, а не точный токенизатор. Заведомо большой запрос
отклоняется без генерации: HTTP 422 `context_limit`. Если Ollama всё же вернула
`finish_reason=length`, её `usage` позволяет отличить заполнение окна от лимита
вывода; последний возвращается как 422 `assistant_output_limit`. История и заявка
не меняются, автоматического повтора нет. При заполненном окне кнопка «Новый диалог»
сохраняет заявку. Контекст не увеличивается автоматически: текущее значение
8192 синхронизировано с `num_ctx` модели в Ollama, резерв вывода — `LLM_MAX_OUTPUT_TOKENS`.

В модель передаётся компактный JSON без графиков, внутренних проверок и скоринга,
последний результат инструмента и текст всех сообщений. JSON каждого старого
ответа не дублируется; статусы предложений остаются в `previous_proposals`.
Полные данные сохраняются в базе и остаются доступны расчётному движку.

Отклонённые и заменённые черновики остаются в истории. Уточняющий вопрос сохраняет текущий неподтверждённый набор данных.

Модель не отправляет заявку и не запускает выдачу. При `AGENT_TOOLS_ENABLED=true` доступны:

| Инструмент | Действие |
|---|---|
| `calculate_loan` | Аннуитетный платёж и переплата по явно заданным сумме, сроку и ставке |
| `assess_credit` | Предварительная оценка текущей заявки на копии |
| `recommend_financing` | Подбор разового кредита или овердрафта на копии |
| `compare_options` | Несколько допустимых сроков с фильтрами платежа или лимит овердрафта по плану; подбор сохраняется отдельно от заявки |
| `simulate_alternative` | Отдельный расчёт с валидированными изменениями полей `need` |
| `web_search` | Публичный поиск Tavily; доступен при заполненном ключе |

`assess_credit` показывается модели только после выбора поддерживаемого продукта.
При отсутствии продукта доступны подбор и отдельный вариант с явно заданным
продуктом. Интерфейс показывает причину отказа инструмента, а не только общую
подпись «не выполнено».

`calculate_loan` вызывает существующий `credit_engine.calculate_loan`: формулы,
проверка входов и округление последнего платежа остаются в движке. Аргументы:
`amount` и `annual_rate_percent` — строки с двумя знаками после точки,
`term_months` — целое от 1 до 600. Например, 30 млн рублей можно рассчитать
вне лимитов каталога без выбора продукта. Неизвестные значения возвращаются в
`missing_fields`, расчёт не выполняется. Ставка не берётся автоматически из
демопродукта. Результат `mode=illustrative`, `saved=false`,
`eligibility_assessed=false`: это платёж без комиссий и страхования, а не оценка
одобрения или минимального оклада. UI показывает отдельную карточку с точными
суммами движка; полный график в контекст модели не отправляется.

Все расчёты используют настоящий `credit_engine`, но банковские проверки остаются
демонстрационными. Инструменты не сохраняют изменения, не подтверждают данные,
не отправляют заявку и не подписывают документы. Успешная оценка заявки помечена
`mode=simulated`, `stage=preliminary`, `saved=false`. Изменение заявки по-прежнему
проходит через карточку подтверждения.

Явная команда рассчитать сохранённую заявку без новых параметров запускает
инструмент непосредственно в приложении; модель вызывается один раз для объяснения.
Для объяснения прямого расчёта в модель передаются потребность, состояние и
результат инструмента без повторных помесячных таблиц. Сам инструмент получает
полный снимок. История диалога сохраняется. Короткое приветствие также требует одного обращения. Если выбор делает модель,
первый запрос содержит нативные определения инструментов. Готовый корректный ответ
без вызовов возвращается сразу. После вызова инструмента либо некорректного JSON
выполняется отдельный запрос финального JSON без инструментов. Новые суммы, сроки,
неоднозначные варианты и поисковые запросы не подставляются в прямой расчёт.
Разделение нужно для используемой GGUF: совместная передача `tools` и
`response_format` позволяла модели пропускать вызовы. Лимит — `AGENT_MAX_TOOL_CALLS`
(сейчас 3); автоматических повторов поиска нет. Отсутствие ключа Tavily отключает
только поиск. Ключ передаётся через окружение контейнера и не попадает в образ,
ответы API, журнал или браузер. Крупные графики и внутренний скоринг исключены
из результатов инструментов. Последний сохранённый результат расчёта доступен следующему
ходу с исходной версией заявки; это не актуальный расчёт для иной версии.

Интерфейс показывает текст, выполненные инструменты, карточку предварительного
расчёта и ссылки из фактической поисковой выдачи. Поле `tools` в сообщении и
раскрываемый блок последнего ответа содержат результат для проверки. Адреса
в поисковом ответе сверяются с фактической выдачей. При выдуманном адресе текст
заменяется нейтральным сообщением, а интерфейс показывает реальные источники. Заявка
справа не подменяется пробным расчётом. Сохранённый диалог можно открыть по
`/chat?chat=<chat_id>`. Ходы с двумя обращениями к модели могут занять больше времени,
чем простой ответ. Время прямого расчёта и выбора инструмента измеряется отдельно.

## API для фронтенда

| Запрос | Назначение |
|---|---|
| `GET /api/chat/config` | Режим, имя модели и ограничения |
| `POST /api/chats` | Новый диалог; `{}` создаёт заявку, `{"application_id":"…"}` использует существующую |
| `GET /api/chats/{id}` | Переписка и актуальная заявка |
| `POST /api/chats/{id}/messages` | `base_chat_version`, UUID `request_id`, `text` |
| `POST /api/chats/{id}/proposals/{proposal_id}/confirm` | `base_chat_version`, `confirmed: true` |
| `POST /api/chats/{id}/proposals/{proposal_id}/reject` | `base_chat_version` |
| `POST /api/chats/{id}/proposals/{proposal_id}/edit` | `base_chat_version`, `base_application_version`, полный оставляемый набор `changes`; пустой набор отклоняет черновик |

Ответ содержит `chat`, `record` (обычный ответ кабинета) и `assistant` (режим и модель). Повтор сообщения с тем же `request_id` и текстом не дублирует историю. Одновременные изменения защищены версиями. При недоступности или некорректном ответе модели API возвращает `503`, переписка и заявка не меняются; сообщение можно повторить.

В одном диалоге до 40 сообщений пользователя, сообщение — до 8000 символов, общий вход модели — до 64 000 символов. Это ограничение тестовой страницы, не оценка размера контекста модели в токенах. «Новый диалог» очищает контекст переписки, сохраняя заявку; предыдущая история остаётся в базе. Переключатель примеров создаёт отдельную заявку.

Провайдер может быть внешним или локальным: заменяются URL, ключ и модель. `LLM_RESPONSE_FORMAT=json_schema` включает схему, `json_object` подходит для API без поддержки JSON Schema; оба ответа проверяются одной моделью Pydantic. Смена формата явная, повторной генерации для исправления ответа нет. Общий бюджет сетевого ожидания хода — `HTTP_TIMEOUT_SECONDS`; максимум одновременных генераций — `CHAT_MAX_CONCURRENT_GENERATIONS` (по умолчанию 2 на процесс). При 429 возвращается `assistant_rate_limited`, при занятости — `assistant_busy`; история не меняется. [Проверка и развёртывание](DEPLOYMENT.md).

Dahl/MiniMax может присылать один начальный блок `<think>…</think>` перед ответом. Адаптер отделяет только полностью закрытый служебный блок; JSON после него по-прежнему проверяется строго. Незавершённый блок, посторонний текст или недопустимые изменения отклоняются. В историю кабинета и frontend рассуждения не сохраняются; при обмене с инструментом исходный ответ остаётся только в памяти текущего хода.

В тестовой странице `/chat` план показывается списком с отдельным редактором. В рабочем кабинете `/cabinet?mode=assistant` предлагаемые значения сразу заполняют поля рабочей области с подсветкой; операции появляются на временной линии и графике. Правки сохраняют неподтверждённый черновик, одна кнопка подтверждает данные и запускает подбор условий. Самостоятельный раздел `/cabinet?mode=manual` ведёт отдельный черновик без вызовов LLM. После выбора условий результат доступен в `/cabinet?mode=applications`.

`POST /api/chats/{id}/proposals/{proposal_id}/preview` принимает `base_chat_version` и рассчитывает предложенные данные на копии. Возвращает `confirmed=false`, `issues` и `result`; историю, заявку и сохранённые расчёты не меняет, модель не вызывает. При неполном плане график доступен, а список предложений пуст. Устаревшие версии и конфликты возвращают `409`; frontend игнорирует ответы для уже сменившегося черновика.

В ответе чата поле `clarification` содержит один следующий вопрос: `question_id`, `field`, `transaction_id`, `title`, `input_type` и `choices`. Вопрос определяется по сохранённым и предложенным значениям, банковские сведения повторно не запрашиваются. Для даты доступны готовые ответы по московскому времени и своя дата, для суммы — ввод рублей. Свой текст отправляется обычным сообщением; модель получает вопрос и ID целевой операции в контексте.

`POST /api/chats/{id}/clarifications/{question_id}/answer` принимает `base_chat_version`, `base_application_version`, `request_id` и ровно одно из `choice_id` или `value`. Готовый ответ без LLM дополняет неподтверждённый черновик и историю. Повтор с тем же `request_id` не дублируется; изменённый вопрос или версия возвращают `409`. Банковские данные и отправленная заявка не меняются. После полного сбора и подтверждения данных рассчитываются варианты соответствующего продукта.

В `overdraft_plan` режим `replace` начинает новый план, `merge` добавляет или исправляет операции по ID. Если при первом обновлении сохранённого плана режим не указан и все ID новые, список заменяет старый после подтверждения; продолжение неподтверждённого черновика накапливает изменения. Банковский остаток не редактируется моделью.
