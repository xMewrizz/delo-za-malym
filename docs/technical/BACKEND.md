# Backend кредитного кабинета

FastAPI связывает формы с кредитным модулем и сохраняет процесс в SQLite. Сейчас доступны разовый кредит на оборотные цели и овердрафт. Используется готовый профиль действующего клиента ООО «Север».

## Запуск

```shell
docker compose up --build -d
```

Интерактивный API: **http://localhost:8000/docs**. Состояние сервиса: **http://localhost:8000/health**. Данные сохраняются в Docker-томе `cabinet_data` при перезапуске контейнера. Остановка: `docker compose down`.

Для разработки с Python 3.13+ и uv:

```shell
uv sync --frozen
uv run --env-file .env --frozen uvicorn backend.main:app --reload
```

По умолчанию база находится в `data/cabinet.sqlite3`. Путь меняется через `DATABASE_PATH`, разрешённые адреса фронтенда — через `CORS_ORIGINS` (адреса через запятую). Docker-порт задаётся переменной `API_PORT` (также поддерживается `APP_PORT`); по умолчанию 8000. Фронтенд на `localhost:5173` и `localhost:3000` уже разрешён. Настройки кабинета — в корневом `.env`, образец — [.env.example](../../.env.example). Compose читает его автоматически. Для лаборатории Ильи можно явно передать `--env-file scr/delo_za_malyn/settings/.env`; не смешивайте два файла при одном запуске. Если 8000 занят, укажите другой `API_PORT` и используйте его в URL API и аргументе `--base-url` проверки сценариев.

## Методы для фронтенда

Все пути ниже начинаются с `/api`. Полная схема: [openapi.json](openapi.json), актуальная схема работающего сервера — `/openapi.json`.

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/profile` | Известные банку сведения о компании и финансовые данные |
| GET | `/products` | Условия разового кредита, овердрафта и рефинансирования |
| POST | `/applications` | Создать черновик с предзаполненными сведениями |
| GET | `/applications` | Список заявок и их состояний |
| GET | `/applications/{id}` | Заявка, расчёты, проверки, история и результат оформления |
| PATCH | `/applications/{id}` | Сохранить подтверждённые изменения формы или ассистента |
| POST | `/applications/{id}/preview` | Предварительный расчёт черновика |
| POST | `/applications/{id}/recommendations` | Подобрать разовый кредит или овердрафт по задаче |
| POST | `/applications/{id}/submit` | Подтвердить, отправить и рассмотреть заявку |
| POST | `/applications/{id}/retry` | Повторить недоступную проверку или обновить истёкшие предложения |
| POST | `/applications/{id}/select-offer` | Выбрать итоговое предложение |
| POST | `/applications/{id}/conditions/{code}/complete` | Смоделировать выполнение поручительства |
| POST | `/applications/{id}/sign` | Смоделировать подписание и выдачу либо открытие лимита |
| POST | `/applications/{id}/cancel` | Отменить заявку до подписания |

В ответе на создание и действия возвращается один объект: `application`, `state`, `checks`, `result`, `readiness`, `recommendation`, `signature`, `completion`, `events`, `submitted_versions`. Интерфейс обновляет эти данные из ответа сервера. `result.status` описывает выполнение оценки, `result.assessment.outcome` — кредитный результат, `state.status` — этап процесса.

При входе по задаче продукт может оставаться `null`: вызывается `/recommendations`, после уточнений и подтверждения выбора применяется продукт через `PATCH`. Рекомендация сохраняется отдельно от итогового решения. Поля и правила: [выбор между продуктами](PRODUCT_SELECTION.md).

Рассмотрение выполняется в рамках запроса. В `events` сохраняются отправка, начало проверок и результат; следующего результата через таймер ожидать не нужно. При технической ошибке проверку повторяет отдельный вызов `/retry`.

## Пример заявки из формы

`POST /api/applications`:

```json
{
  "need": {
    "purpose": "working_capital",
    "preferred_product": "working_capital_loan",
    "requested_amount": "500000.00",
    "term_months": 12
  }
}
```

Из ответа сохраняем `application.application_id` и `application.application_version`. Профиль и история финансов уже заполнены. Для расчёта выбирается один из трёх продуктов; у овердрафта заполняется `product_details.overdraft` по [его контракту](OVERDRAFT.md), у рефинансирования — `product_details.refinancing.loan_ids` по [контракту замены долгов](REFINANCING.md).

Изменение через `PATCH /api/applications/{id}`:

```json
{
  "base_application_version": 1,
  "changes": {
    "need.requested_amount": "700000.00",
    "need.term_months": 18
  }
}
```

Можно передавать отдельные поля `need.*`, `financials.*` либо целиком разделы `need`, `financials`, `product_details`. Целый раздел **заменяется**, а отдельные поля обновляются по указанному пути. После сохранения версия увеличивается, подтверждение и прежние предложения сбрасываются. Отправленные версии остаются в `submitted_versions`. Регистрационные сведения берутся из профиля клиента. `client_data` содержит источник и время получения, снимок `bank_financials` и сведения кредитной истории. Полученные из банка значения не заменяются клиентским PATCH или CSV: ошибка `bank_data_read_only` (422). Допускается дополнение отсутствующих значений, исходный банковский снимок сохраняется.

Для `/preview`, `/recommendations` и `/retry` тело — `{"base_application_version": 2}`. Для `/submit` и `/cancel` требуется также `"confirmed": true`.

Для `/select-offer` передаются `base_application_version`, `assessment_id` и `offer_id` из итоговой оценки. Для `/sign` и выполнения условия — `base_application_version`, выбранный `offer_id` и `confirmed: true`. Завершение условия `guarantee_required` моделируется отдельным явным действием; менять `conditions.fulfilled` в полученной оценке не нужно.

Подписание проверяет предложение повторно и возвращает `disbursed` с графиком платежей либо `limit_opened`. Если условия не выполнены или предложение истекло, ответ содержит соответствующее состояние без подписи и выдачи. Повтор подписания того же завершённого предложения возвращает сохранённый результат с тем же `operation_id`.

Ошибка HTTP 409 означает конфликт версии или недопустимое действие: нужно загрузить актуальную заявку. 422 — ошибка тела запроса, 404 — неизвестная заявка или сценарий. Ошибки кредитных данных приходят внутри `result` и отображаются возле соответствующих полей.

## Проверка и демонстрация

`GET /api/demo/scenarios` возвращает 14 примеров. `POST /api/demo/scenarios/{product}/{scenario_id}` создаёт новый черновик выбранного примера. После этого он проходит те же методы и реальные расчёты, что обычная заявка. Даты планов и финансовых периодов подстраиваются под текущую дату.

Проверить запущенный сервер, включая оформление положительных решений:

```shell
python -m scripts.run_api_scenarios
```

Все тесты, включая сохранение после перезапуска, конфликты версий и параллельное подписание:

```shell
uv run --frozen python -m unittest discover -s tests
```

SQLite хранит агрегат заявки как JSON и обновляет его в транзакции `BEGIN IMMEDIATE`: проверка версии, готовности к подписанию и запись результата выполняются под одной блокировкой записи. Схема хранилища имеет версию `PRAGMA user_version=1`. Приложение стартует с одним демонстрационным клиентом; внешние банковские проверки, поручительство, подписание и денежные операции моделируются внутри сервиса.

## Полученные кредиты и календарь

`GET /api/calendar` возвращает `events` (выдача, открытие лимита и ожидаемые платежи), `accounts` (полученное финансирование) и `plans` (поступления и расходы по отдельным заявкам). Интерфейс совмещает общие платежи с одним выбранным планом. Поле `forecast` отличает ожидаемые события от выполненной операции симулятора.

События банковских кредитов содержат `loan_id` из профиля. События полученных через кабинет продуктов связаны с `application_id`. Эти идентификаторы позволяют фильтровать календарь по одному продукту без сопоставления названий; кредит, уже связанный с заявкой, не показывается повторно среди банковских продуктов.

Источником новых обязательств служит сохранённая `completion` с графиком выдачи. При выдаче существующие незавершённые заявки того же клиента атомарно получают обновлённые обязательства и остаток, новую версию и запрос пересчёта. Отправленные снимки сохраняются. Старые версии и предложения нельзя подписать. В новые заявки обязательства подставляются из профиля. Известные банковские графики включаются в будущие расходы с устойчивыми идентификаторами без повторного добавления. Сценарии `/api/demo/scenarios` используют изолированные тестовые профили и не пополняют общий портфель клиента.

Рефинансирование сохраняет `completion.repaid_loans` и новый график одной транзакцией. В `accounts` прежний кредит получает `status: "refinanced"`, нулевой долг и `refinanced_by`; действующий — `status: "active"`. События `loan_refinanced` и `refinancing_completed` имеют `direction: "none"`: средства направлены на погашение долгов, остаток на счёте не увеличивается. Прежние будущие платежи исключаются, следующие расчёты учитывают новое обязательство.
